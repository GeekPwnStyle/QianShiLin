# 2026-11-19 concurrency benchmark and first optimization

Production source baseline: 0701db4. Isolated Docker network and schema-only PostgreSQL clone; synthetic 50,000 users/sessions and 100,000 customers. No production customer data copied. Same host as production, therefore intentionally capped: API 1 CPU/512 MiB, DB 2 CPU/2 GiB (1.2 GiB tmpfs), generator 0.5 CPU/256 MiB. This is a short comparative baseline, not a production capacity or 50,000 simultaneous-user certification.

Read workload: round-robin session, customer first page, keyword 9876, page 4000; page size 20. Closed-loop concurrency 1/10/30, 10 seconds each. One authenticated synthetic principal (50,000 stored users is not 50,000 active identities). Excludes proxy/TLS/browser/network, login storms, production-size order history, disks and mixed production writes. First unauthorized calibration was discarded; published runs are all HTTP 200. Raw results in adjacent JSONL files.

Read improvement is the combined effect of added indexes/configuration, not an isolated attribution. No repeated statistical trials; cold starts/cache and same-host resource variation can affect results.

Write comparison: each version creates 20 inbound drafts with 100 lines at concurrency 5, 20/20 HTTP 201. p50 80.6 -> 77.6 ms; p95 1581.7 -> 1520.4 ms. No strong speedup claim from this short sample. Both runs combined verified 40 headers, 4,000 lines, quantity 8,000, amount 24,000. Batched insert reduces SQL round trips per 100-line draft from 100 to one without changing transaction boundary.

Changes: environment-configurable pool size (still 10), 2s connection wait, 15s statement/idle-transaction timeout, 3s lock timeout, idle pool error handling, 100 active request ceiling with 503/Retry-After, transient DB failures mapped to 503; in-flight accounting released in finally even if caller disconnects. Customer store/date/id ordering index and GIN trigram index across the five existing search columns. Concurrent index migration 020 must run outside a transaction; verify no invalid index after interruption. Wider GIN indexes add write/storage cost: measure this next.

Benchmark helpers are for DISPOSABLE environments only. Seed requires production schema-only restore; do not run on production. Set role permissions to basic.customer.read/basic.customer.create/basic.customer.update/purchase.read/purchase.create, map perf1 session hash to SHA256(hex('perf-perf1').padEnd(64,'0')), and create supplier 11111111-1111-4111-8111-111111111111 before write benchmark. Helpers use private DNS qsl-perf-api and a known synthetic token deliberately confined to the private test network. Never expose this test instance publicly.

Next stage: separate load generator/host and realistic disk; multiple distinct authenticated users and increasing fixed arrival rates; 10-30 minute repeated runs; per-endpoint metrics, pg_stat_statements, EXPLAIN ANALYZE BUFFERS; cursor pagination and count strategy; optimistic concurrency and idempotency contracts; migration-only startup (remove request-path DDL); polling jitter/backoff; inventory/financial hot-row tests; API replica and failover tests. Define business SLO and reserve headroom before approving launch scale.

Overload test: isolated API configured with QSL_MAX_IN_FLIGHT=1; concurrency 10 returned 149 HTTP 200 / 33,226 HTTP 503, concurrency 30 returned 156 HTTP 200 / 41,125 HTTP 503. These high rejection rates are intentional validation of the limiter, not useful business throughput. Sequential phase returned 160/160 HTTP 200. Published normal benchmark uses default ceiling 100. Frontend typecheck and release-script Vite build passed; no UI behavior changed and no browser interaction regression was performed.
