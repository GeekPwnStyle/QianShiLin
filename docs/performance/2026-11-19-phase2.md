# 2026-11-19 phase 2: 500 successful requests/sec target

Source baseline d9fb4f8. Same-host isolated private Docker network; PostgreSQL disk-backed with 3 CPU / 4 GiB cap, API 2 CPU / 1 GiB, load generator 1 CPU / 512 MiB. Synthetic 50,000 stored users and 100,000 customers. Round-robin 100 authenticated identities. Production data never copied except schema. Traffic does not traverse production proxy/TLS.

Workload: 80% customer lists (first page, keyword 9876, page 4000, keyword 1234), 15% session reads, 5% inbound draft creation with ten lines each. All users share a store scope. Fixed offered arrival rate; latency measured from dispatch through full body receipt, generator socket queue included. A 10 ms scheduling tick batches arrivals. This is a hot-query business mix; it is not 500 arbitrary uncached queries/sec, 500 writes/sec, or 50,000 active users. Read cache TTL is one second. Customer writes invalidate the cache on entry and completion. Direct database changes and other processes can remain stale for up to the TTL; do not use this cache for balance, stock or financial decisions.

Baseline: offered 50/sec for 20 sec, 1,000 requests all successful, completion including drain 23.76 sec, effective 42.09 successful/sec, p95 4258 ms. Optimized cold-start 500/sec for 30 sec: 14,995 successful, five 503 overload rejections; effective 498.85/sec, p95 931 ms. Preserve this result; it does not meet a zero-error cold-start objective.

Optimized steady test: offered 550/sec for 120 sec; 66,000/66,000 successful (62,700 HTTP 200 and 3,300 HTTP 201); effective 549.46 successful/sec; p50 5.51 ms, p95 9.84 ms, p99 68.56 ms. Maximum pending 69. Sustained repeat results stored adjacent. These are short same-host tests with significant query reuse, not an internet-facing production capacity SLA. Baseline and optimized samples differ in offered load and cache warmth; speedup should not be interpreted as an isolated SQL-only speedup.

Changes: customer lists use deferred join (page over narrow id/date keys, then fetch wide records). One-second, 256-entry/32 MiB bounded process-local cache with single-flight loading. Keys contain complete authorized store scopes, filters and pagination. Authorization is checked against DB before each lookup; cached raw rows are shaped/redacted separately per caller. Customer mutations invalidate globally before and after execution. Generation guard prevents old in-flight loads repopulating after invalidation. Eviction limits retained cache payload, not total process heap or all in-flight responses. Multi-replica deployments rely on TTL unless shared invalidation is added.

Validation: automated tests cover single-flight, scope-key separation, invalidation of pending loads, expiry, loader errors and memory bound. API regression uses a dedicated other-store user after warming the primary store cache and confirms zero rows/total. Typecheck passes. Inbound headers/lines and sums checked in isolated DB. No UI contract changes or browser interaction tests in this patch.

Next: cold diverse search terms and customer-write-heavy profiles; cursor pagination and exact-count redesign; fixed multi-store tenant distributions; transaction idempotency/optimistic versions; migration-only startup; external load generator with TLS and longer soak; distributed invalidation before horizontal scaling. Report cold-start overload explicitly. Avoid using 503 throughput as business success.

Repeat: 550/sec for 180 sec; all 99,000 successful (94,050 HTTP 200, 4,950 HTTP 201), effective 549.47/sec, p95 10.33 ms, p99 68.51 ms. Mutation integration regression warms list, POSTs batch-visit for one customer, then confirms changed row immediately. Diverse low-selectivity/no-match six-digit keyword test at 50/sec for 20 sec completed 1,000/1,000 successfully, p95 11.40 ms; this does not establish 500/sec broad uncached search capacity. Two steady runs combined contain 8,250 successful ten-line draft writes. All benchmark JSONL retained including cold-start rejection sample.
